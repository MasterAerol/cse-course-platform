# PasaWise Authentication UX v2

Authentication UX v2 adds pending email/password registration and six-digit
email verification while retaining server-verified Google Identity Services
and explicit Google account linking.

## Security model

- `POST /api/auth/register` creates or refreshes only a
  `pending_registrations` record. It does not create a user, enrollment, or
  session and does not set an authentication cookie.
- The code is six digits, expires after 10 minutes, is single-use, and is
  protected by a maximum of five attempts.
- A code can be resent after 60 seconds. A resend replaces the stored HMAC and
  immediately invalidates the previous code.
- The database purpose is `EMAIL_REGISTRATION_VERIFICATION` and the code is a
  purpose-bound HMAC-SHA-256 digest using
  `EMAIL_VERIFICATION_SECRET`; it never stores the six-digit code.
- Verification sends are limited independently by IP and opaque pending
  registration ID. Initial registration is limited by IP and normalized email.
- Only `POST /api/auth/register/verify-email` atomically creates the active
  learner, verified email state, free CSE enrollment, latest learner session,
  and session cookie while consuming the pending registration.
- A correct password for a pending registration returns
  `EMAIL_VERIFICATION_REQUIRED` so the Login UI can resume verification.
  An incorrect password retains the generic invalid-credentials response.
- Google registration continues to rely on server-side Google ID-token
  validation. A Google claim with `email_verified=true` records verification
  method `google`; no Google Client Secret is used.
- Existing active users are preserved. Migration 0019 labels Google-identity
  users as `google`, labels other pre-v2 users as `legacy`, and ensures those
  existing accounts retain verified/login status.

Expired pending registrations are deleted lazily during registration,
verification, and resend operations. A pending record has a 24-hour maximum
lifetime, after which registration must be started again.

## Resend transactional email

The Worker sends verification mail through the shared
`TransactionalEmailService` abstraction. The adapter posts text and HTML
content to `https://api.resend.com/emails`; authentication code does not
contain Resend-specific logic. The API key is read only from the
`RESEND_API_KEY` Cloudflare secret. The production From address is
`PasaWise <noreply@pasawise.com>`, and it must not be used until Resend marks
`pasawise.com` verified.

Production activation requires an operator to complete these prerequisites:

1. In the Resend dashboard, add `pasawise.com` as a sending domain and select
   the appropriate sending region.
2. Publish every DNS record shown for that domain. Resend domain verification
   requires:

   - the SPF TXT record;
   - the MX record associated with the SPF/Return-Path configuration; and
   - the DKIM TXT record.

   Use the exact names and values generated by Resend; they are domain- and
   region-specific. Add a DMARC TXT record as a recommended deliverability and
   anti-spoofing control if one is not already present.
3. Wait until the Resend dashboard reports the domain as verified before using
   `noreply@pasawise.com`.
4. Create a Resend API key scoped to sending mail. Copy it once and do not place
   it in source control or plaintext Worker variables.
5. Upload it to the existing Worker as a Cloudflare secret:

   ```text
   npx.cmd wrangler secret put RESEND_API_KEY
   ```

   `wrangler.jsonc` declares only the required secret name. The key itself
   must never appear in `wrangler.jsonc`, `/api/config`, frontend code,
   application logs, or client responses.
6. Keep the existing `EMAIL_VERIFICATION_SECRET` Cloudflare secret present; it
   remains the independent HMAC key for verification-code hashing.

Resend references:

- https://resend.com/docs/send-with-cloudflare-workers
- https://resend.com/docs/api-reference/emails/send-email
- https://resend.com/docs/dashboard/domains/introduction

## Migration and release gate

Migration 0019 is required before this Worker code can be deployed:

```text
npm.cmd run db:migrate:remote
```

Do not deploy the code before the migration, Resend domain verification, and
required Worker secrets are complete. The approved release path remains Safe
Release; do not bypass it.

Production remains fail-closed until explicitly opened in both controls:

- `REGISTRATION_MODE=closed`
- Admin `public_signup=0`

The unrelated commercial controls remain unchanged:

- `show_pricing=0`
- `public_checkout=0`
- `premium_access_enforcement=0`

With either registration control closed, manual registration initiation,
verification, resend, and brand-new Google registration all fail closed.
Existing password users and already-linked Google users can still sign in.
